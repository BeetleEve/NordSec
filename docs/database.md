# База данных NordSec

PostgreSQL используется и для работы, и для тестов. Модели описаны в
`apps/accounts/models.py` и `apps/aid/models.py`; операции — в `apps/aid/services.py`.

## Таблицы

| Таблица | Назначение |
| --- | --- |
| users | Учётные записи, роль, текущий профиль |
| contacts | Контакт для конкретной передачи: имя и телефон |
| categories | Категории вещей |
| items | Объявления, состояние и местонахождение вещей |
| requests | Заявки на выбранные вещи и прежние ручные обращения |
| reservations | Согласованные резервы и время встречи |
| delivery_tasks | Поручения волонтёрам |
| transfers | Подтверждения фактического получения |
| volunteer_applications | Анкеты кандидатов в волонтёры |
| favorites | Связь пользователя с избранной вещью |
| notifications | Уведомления личного кабинета |
| activity_log | История операций и их исходные состояния |
| access_attempts | Ограничение частых запросов входа и восстановления |

Также Django использует девять таблиц для групп, прав, сессий, миграций и
журнала административной панели. Всего 23 таблицы: нормализация добавила одну
общую таблицу контактов. Количество таблиц само по себе не определяет нормальную форму.
`users_groups` и `users_user_permissions` — связи пользователей с группами и правами.

## Нормализация и зависимости

В основных отношениях каждое поле зависит от ключа своей записи.
Категория вещи хранится только в `items.category_id`, её название — в `categories`.
У заявки с выбранной вещью категория вычисляется через `preferred_item_id`.
`unselected_category_id` используется только у старых или ручных обращений без
выбранной вещи. Ограничение CHECK запрещает одновременно сохранять два источника
категории или не сохранять ни одного. Посетители создают заявки только из карточки вещи.

Имя и телефон для передачи вынесены в `contacts`. Одинаковая пара имени и телефона
хранится один раз (UNIQUE). Изменение контакта одной записи создаёт или выбирает
другой контакт, не изменяя остальные объявления и обращения.
Контакт передачи и текущие контакты профиля — разные факты: пользователь может
указать для передачи другого человека. Поэтому изменение профиля не переписывает
контакты ранее согласованной передачи.

Район поручения вычисляется через резерв и вещь, отдельной колонки больше нет.
Адреса в поручении — согласованный маршрут конкретной поездки; они могут отличаться
от исходных адресов объявления и заявки и потому сохраняются самостоятельно.
Время принятия вещи и время её проверки также обозначают разные события.

Связующие таблицы имеют уникальные пары ключей. Частичные уникальные индексы
запрещают два действующих резерва на одну вещь или заявку. Один резерв имеет максимум
одно поручение и одно подтверждение передачи. Внешние ключи защищают историю от удаления.

Журнал событий хранит JSON-снимки как неделимый документ события. Это технический
архив, а не источник актуальных контактов, ролей или состояний. Формальное доказательство
3НФ для произвольного содержимого JSON не заявляется. Нормализация основных отношений
не означает удаление исторических фактов из журнала.

## Перенос существующей базы

Миграции 0003–0006 приложения aid переносят контакты, устраняют повтор категории
и района, переименовывают таблицы. Миграции accounts переводят роль coordinator в
moderator и переименовывают таблицу пользователей. Идентификаторы и связи сохраняются.

Перед обновлением остановите работающий сервер приложения, создайте резервную копию
через `python scripts/backup.py` при работающей PostgreSQL, затем примените
`python manage.py migrate` и перезапустите приложение. Для локального запуска
`python main.py` выполняет миграции автоматически. Для отката используйте полную
резервную копию; удалённые колонки не следует восстанавливать отдельным SQL вручную.

Приложенная демобаза пересобрана из публичных фиктивных данных на новой схеме.
В неё не экспортируются личные записи из локальной базы разработчика.

Названия таблиц даны короткими английскими словами без технических префиксов.
Русское назначение записано в комментариях PostgreSQL и отображается в свойствах
таблицы в pgAdmin. Служебные таблицы Django сохраняют стандартные имена.

`requests.preferred_item_id` обозначает первоначальный выбор, `reservations.item_id` —
вещь, назначенную в конкретном резерве. Это особенно важно для старых ручных обращений:
у них нет выбранной вещи, а последовательные резервы могут относиться к разным вещам.
Поэтому request_id не определяет item_id для всех исторических резервов; ссылка
на фактически резервировавшуюся вещь сохраняется. Для новых заявок на выбранную вещь
сервис запрещает подменять её при резервировании.

## Переход к карте

Миграции aid 0008–0009 добавляют placement, координаты, точность, срок уличной метки
и таблицу item_signals. Координаты должны присутствовать парой и быть в допустимых
диапазонах. item_signals хранит по одной последней отметке пользователя на объявление.
Новые обращения и резервы для карты не создаются; прежние таблицы сохранены как архив.
Контакт владельца остаётся в нормализованной contacts. Уличные записи не копируют туда
его имя и телефон. В публичном API домашние координаты округляются до запроса по области.
